# Open gaps — ACP port + cross-platform pivot (2026-06-16)

**Purpose.** A single inventory of in-flight, incomplete work so nothing is lost as focus
shifts to the **llama.cpp serving pivot** and broader cross-platform work. This is a *gaps*
list (what's left), not a design — each area points at the doc that owns its design.

**The pivot that frames everything (2026-06-16):** retire the vendored **mistral.rs** brain;
adopt a prebuilt **`llama-server` subprocess sidecar** behind the existing `ProviderAdapter`
seam (cross-platform serving: Metal/CUDA/Vulkan/ROCm; Gemma 4 12B via Unsloth dynamic GGUF
quants; runtime GGUF-LoRA). Validated end-to-end today (base ↔ personalized via per-request
LoRA scale on one server). Design: [`cross-platform-brain-llamacpp-2026-06-16.md`](./cross-platform-brain-llamacpp-2026-06-16.md)
(supersedes [`cross-platform-overnight-training-2026-06-16.md`](./cross-platform-overnight-training-2026-06-16.md)).
This makes the **daemon the cross-platform spine**: it will supervise *two* subprocess sidecars
(llama-server + per-turn ACP agent servers) under the existing `DaemonProcessRegistry` +
parent-watch.

## A. Native ACP client in the Rust daemon — IN FLIGHT (branch `acp-native-rust`, commit 101146cd, not pushed)

Moving ACP delegation out of Swift (`acpx exec`, macOS-only, one-way) into the daemon as a
native cross-platform ACP client. Plan: `~/.claude/plans/smooth-hopping-kettle.md`.

**Done & gated (green `cd crates && just check`):**
- **`crates/fae-acp`** — ACP client on Zed's `agent-client-protocol` 0.14 crate: spawns an
  agent ACP server (`gemini --acp`, `npx claude-code-acp/codex-acp/pi-acp`), drives
  `initialize → session/new → session/prompt`, accumulates streamed text + tool calls, answers
  permission requests per policy. `run_one_shot(...) -> AcpOutcome`. **Proven live vs gemini**
  (`pong`, `end_turn`, ~27s).
- **Daemon command surface** — `Scope::AgentExecute` + `agent.run` (one-shot) + `agent.list`
  in `fae-daemon/src/session.rs` dispatch; 21 daemon tests pass.

**Gaps (remaining stages):**
- **A1 — Swift thin client (rest of Stage 1).** Repoint `AgentDelegateTool.swift` at the daemon
  `agent.run` via the existing `DaemonSocketConnection` (reuse `DaemonLLMEngine.swift` socket +
  `session.authenticate`); the Swift bootstrap client must be granted the **`AgentExecute`**
  scope. Keep the old Swift subprocess path behind a flag as fallback. Then a live in-conversation
  `delegate_agent` through `run-dev`. *Needs the daemon rebuilt + re-embedded with `agent.run`.*
- **A2 — Streaming + persistent sessions (Stage 2).** Daemon control protocol is request/response
  only; add **interim event frames** (same `request_id`, an `event` field, before the final `ok`)
  and a streaming variant of the Swift `roundTrip` so agent output narrates on the orb. Add
  `agent.session_start/prompt/cancel/close`. Migrate `AgentSessionTool`; **delete Swift
  `ACPSessionManager`**.
- **A3 — Permission round-trip + fs mediation (Stage 3, the payoff).** Add **server-initiated
  requests** (daemon → Swift, awaiting a reply); wire ACP `session/request_permission` → Fae's
  approval card, and `fs/read_text_file` / `fs/write_text_file` → gated by `DamageControlPolicy` /
  `PathPolicy`.
- **A4 — Conductor seam + polish (Stage 4).** Expose `AcpClient` behind the future conductor's
  `Acp` Runner; error differentiation (auth / rate-limit / network); attachments; agent
  install/discovery (mirror `acp-setup`); delete dead Swift `ACPProtocol.swift`.

**Interaction with the pivot:** ACP agents and llama-server are both subprocess sidecars under
`DaemonProcessRegistry`. The Stage-2 streaming protocol extension and the llama.cpp serving
adapter both want daemon-side **SSE/streaming** — design them together so the control plane gets
one streaming mechanism, not two.

## B. llama.cpp serving swap — NEW, design complete, unbuilt

Owner: [`cross-platform-brain-llamacpp-2026-06-16.md`](./cross-platform-brain-llamacpp-2026-06-16.md)
(§2 `LlamaServerAdapter`, §5 daemon protocol, §8 phasing). Gaps:
- **B1 — `LlamaServerAdapter`** — ✅ **LANDED** (branch `llamacpp-serving-adapter`, not committed).
  `crates/fae-engine/src/llamacpp_adapter.rs`: `ProviderAdapter` impl streaming OpenAI HTTP/SSE
  → `ChatEvent`; `connect` (attach) + `spawn`/`LlamaServerHandle` (supervise child, health-wait,
  kill-on-drop); pure `build_chat_body` (system/messages/**input_audio**/tools) + `events_from_chunk`,
  both unit-tested. Wired into `fae-daemon` `build_engine` via `FAE_ENGINE=llamacpp` + `FAE_LLAMA_*`
  env (attach to a URL **or** spawn). reqwest added (loopback, no TLS). **Verified:** 20 fae-engine
  tests pass (6 new), clippy `-D warnings` clean (fae-engine + fae-daemon), fmt clean, and a **live
  smoke** streamed real turns through the adapter against `llama-server` ("Edinburgh"; 63-event
  multi-chunk stream). *Deferred to B3:* per-request LoRA `scale` field (body doesn't set it yet).
  *Deferred to B2:* `models.lock` verification of the GGUF/mmproj paths (env-read for now, noted in
  `build_llamacpp_engine`). *Streaming-reuse (E):* SSE→event parse lives in the adapter; lift into a
  shared module when ACP-A2 needs it.
- **B2 — Ship/resolve the `llama-server` binary** per platform (bundled on macOS; discovered/
  installed elsewhere) + the **Gemma 4 12B Unsloth dynamic GGUF** (UD-Q3/Q4_K_XL) under
  `models.lock` (fail-closed checksums).
- **B3 — Runtime GGUF-LoRA per-request scale** — ✅ **adapter level LANDED** (commit e583b517).
  `ProviderAdapter::set_adapter_scale` (no-op default); `LlamaServerAdapter` emits per-request
  `lora:[{id,scale}]` + flips it via an interior-mutable atomic; personalization on-by-default when
  a LoRA is loaded (`spawn` from config, or `FAE_LLAMA_HAS_LORA` on `connect`). **Verified:** +2
  unit tests; deterministic live A/B (same server, scale 0 → base refusal, scale 1 →
  MOONLIT-…HERON) with the adapter's exact `lora` field.
- **B3b — daemon protocol toggle** — ✅ **daemon side LANDED** (commit b7477a2f). New
  `Scope::ModelManagement` (granted to `SwiftFrontend`) gates `engine.set_adapter_scale {scale}`
  in fae-control-plane `required_scopes` + fae-daemon `session.rs` dispatch → `set_adapter_scale`.
  +3 tests; 46 control-plane+daemon tests pass.
- **B3b — `engine.reload`** — ✅ **LANDED** (commit 41157018). `ProviderAdapter::reload_adapter`
  (async; default rejects). `LlamaServerAdapter` manages its sidecar via interior-mutable
  `Sidecar{handle,config}`; reload kills the old child, rebinds the same port, respawns with the
  new `--lora` (LoRA presence + scale as atomics). `engine.reload {personal_adapter}` command gated
  on `ModelManagement`. **Verified:** 70 tests (+3); **live de-risk** (`examples/llama_reload`) —
  managed spawn → reload(personal.gguf) → serve, sidecar restarts + rebinds same port. The daemon
  now has the full deploy primitive (nightly loop: produce `personal.gguf` → `engine.reload`).
- **B3b — Swift client: DEFERRED by design** (2026-06-16). The personalized brain needs **no Swift**
  (daemon spawns llama-server with the LoRA; B3 scale defaults to 1.0 = on). `set_adapter_scale`/
  `reload` are the control surface, and their real consumer is the nightly deploy/eval loop, which
  must first produce a **GGUF** adapter (gap C2). Wiring Swift now would (a) be premature (no GGUF
  to deploy yet) and (b) add Swift we intend to migrate to the daemon. When the loop moves
  daemon-side it drives `engine.reload`/`set_adapter_scale` itself; a manual "use base" knob can be
  a daemon CLI/diagnostic, not a Swift path. **→ Next is gap C2 (training → PEFT → GGUF), the
  producer.**
  > **Finding (feeds gap C):** the toy test-LoRA was trained on a *direct* `Q→A` format and its
  > effect is muted on the `--jinja` **chat** path (Gemma emits `<|channel>thought` reasoning that
  > derails the overfit mapping) — it fired cleanly only on raw `/completion`. **Real personal
  > adapters must be trained including the chat/thinking template**, not bare turns, or the LoRA
  > won't surface through the served chat endpoint.
- **B4 — Retire mistral.rs/candle**: remove the vendored `[patch]` blocks + the daemon's
  mistral.rs adapter + the Metal-NaN/padded-retry machinery once llama-server is the sole engine.
  *(Cross-references §B in the pivot doc; big deletion, gate behind B1–B3 shipping.)*
- **B5 — Audio-in path**: Gemma 4 audio via llama.cpp (merged USM Conformer, build b8766) vs the
  current two-pass daemon ASR — decide and wire (affects the whole PTT→LLM lane).

## E. Cross-cutting / sequencing notes
- **One streaming mechanism.** ACP Stage-2 streaming (A2) and the llama-server SSE adapter (B1)
  both need daemon-side streaming frames — design the control-protocol streaming extension once.
- **Daemon = the spine.** Both new sidecars (llama-server, ACP agents) ride `DaemonProcessRegistry`
  + parent-watch; verify orphan-kill covers *all* children, not just the daemon.
- **`models.lock` fail-closed** must cover the new GGUF base + any bundled `llama-server` (B2) the
  same way it covers today's mistral.rs snapshot.
- **`env -u RUSTFLAGS`** for all crates builds (vendored candle's unused-import breaks `-D warnings`
  — and goes away with B4).
- **Suggested order:** finish ACP Stage-1 Swift (A1, small, ships usable delegation) → B1–B3
  (llama-server adapter + GGUF + LoRA, the brain pivot) → A2/B-streaming together → C (training
  loop onto the new brain) → B4 mistral.rs retirement → A3/A4 + D portability.
